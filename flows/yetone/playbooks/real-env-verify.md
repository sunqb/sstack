# 真实环境验证

公开实践里，验证指的是在用户出问题的那一层实际跑过，而不是模型声称已经修好。

建议最低标准：

1. 先按报告者的环境、入口和数据复现，再改代码。不要只用自己构造的近似样本。
2. 跑 `bash scripts/verify.sh`，再加上项目在 `docs/code-standards.md` 里列出的额外命令。
3. 提交说明写清：在哪份代码上跑了什么、输出是什么、手工试了什么、哪些没试。没跑的写成未跑。
4. 标签或发布等到一次绿色运行之后。不要在红测试上发布，也不要把「和 main 一样红」当成可以合并的理由——那是一个现在就要登记的缺陷。
5. 若产品跨多个操作系统或客户端，在受影响的每一端复现。yetone 提到过为自己的桌面产品准备 macOS、Windows 和 Linux 环境（评论区转述，见 README 来源节）。你的项目若只跑在一个环境，就把那一个环境准备好，不必照搬三台机器。
6. 没在真实路径上验证过的功能，不要对用户说已经可用。
