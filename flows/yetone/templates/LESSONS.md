# Lessons from merged work

本项目的改动由 agent 协助编写、审查和合并。定期（建议每天或每个发布周期结束时）复盘新提交，只记三件事：

- 哪些后来又被修过一遍
- 哪些本来不该合并
- 哪些验证做得太薄

改代码之前先读这份文件。

## 格式（不要改这个约定）

每一条教训是：

1. 一条规则（加粗的一句话，告诉以后的 agent 该怎么做）
2. 为什么，以及用户能看见的后果
3. 证据（issue、commit、复现步骤）
4. 可选：后来做对的例子（Done right）
5. `Seen N× (YYYY-MM-DD, …)`：按**审查再次发现它的不同日期**计数，同一天发现多次只算一次

一条教训在 **3 个或更多个不同日期** 被看到之后，把规则搬进 [docs/code-standards.md](docs/code-standards.md)，并在文末「Moved to the code standards」留下索引。升格后以 code-standards 为准，审查仍要检查它。

下面的示例是虚构的，换成你项目里的真实证据。没有证据的条目不要留。

## Verification

**去掉这处改动之后，专门为它写的测试必须失败。编译失败或被 skip 不算。**

- 示例：2026-01-02 合入了「空标题应被拒绝」，但测试只断言函数返回值，把校验删掉后测试仍绿。用户仍能存入空标题。补了一条从界面提交空标题的测试后才算数。
- Seen 1× (2026-01-02).

## Merging and closing

**合并记录的是在所审查的那份代码（reviewed head）上实际跑过的命令和输出，而不是「和 main 一样」或「以前跑过」。**

- 示例：2026-01-05 的提交说明写了测试已通过，跑的却是前一个提交。随后在 reviewed head 上复跑失败。
- Seen 1× (2026-01-05).
