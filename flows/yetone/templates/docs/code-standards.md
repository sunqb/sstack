# Code standards

这里只放已经从 [LESSONS.md](../LESSONS.md) **升格**的规则：同一条教训在 3 个或更多个不同日期被复盘看到。审查时逐条对照；不满足的 PR 应指出是哪一条。

子系统如何描述和审查，见 [subsystems/README.md](subsystems/README.md)。已拍板的产品决定见 [design.md](design.md)。

项目刚初始化时下面几乎是空的，这是正常的。不要把尚未反复出现的教训提前写成硬规则。

## 验收（每次合并或发布都要交代）

下面几条是对 yetone/magpie `docs/code-standards.md` 验收精神的转写，用于任意项目。改动只有在说明了「跑了什么、打印了什么」之后才能合并或发布。**没跑的检查写成未跑，不要省略。**

1. 有一条在去掉本次改动后会失败的测试（编译失败或 skip 不算）。
2. 跑完项目约定的全量检查（`bash scripts/verify.sh`，以及你在本页列出的额外命令），而不是只跑「自己以为碰到的包」。
3. 在改动所影响的真实环境里做过一次使用（用户实际使用的系统、配置或入口）。没做的写明未做，且不要对用户声称该路径可用。
4. 较大的提交在说明里写清：实际跑了什么、手工试过什么、哪些没有试。
